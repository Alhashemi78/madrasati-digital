# تطبيق إصلاحات مدرستي الرقمية

هذه الملفات تعديلات كود محلية قابلة للمراجعة. تجهيزها أو نجاح اختباراتها لا يعني نشرها على GitHub أو تطبيقها في Supabase.

## المشروع الموجود حاليًا

المستودع: `Alhashemi78/madrasati-digita`، الفرع `main`.

رابط البوابة المتوقع: https://alhashemi78.github.io/madrasati-digita/

رابط الفعاليات المتوقع: https://alhashemi78.github.io/madrasati-digita/school-events/

1. ارفع ملفات الواجهة المعدلة إلى المستودع، وتحقق من نجاح نشر GitHub Pages في صفحة Actions.
2. من Supabase Auth > URL Configuration أضف رابط الفعاليات الجديد إلى Redirect URLs. إن كان Site URL ما زال يشير إلى المسار القديم فحدّثه. تغيّر مسار الموقع؛ أصل الموقع `https://alhashemi78.github.io` لم يتغير، لذلك لا يتطلب تغيير CORS لخدمة الصور.
3. انشر مصدر `supabase/functions/school-events-images/index.ts` المحدث في Edge Function باسم `school-events-images`. يحتفظ بأسرار الخادم الحالية؛ لا تنقلها إلى المتصفح. المصدر المحدث يقرأ الصلاحيات والفعالية والتوثيق بهوية المستخدم، ثم يسجل بيانات الصورة بمفتاح الخدمة داخل الخادم فقط. امنح `service_role` صلاحية `select,insert` على `public.school_event_photos` إن لم تكن موجودة.
4. **بعد نشر خدمة الصور المحدثة**، شغّل `school-events/photo-metadata-hardening.sql` من SQL Editor. يمنع تسجيل بيانات صور مزورة مباشرة من المتصفح، دون حذف الصور أو سجلاتها. تشغيله قبل تحديث الخدمة القديمة قد يعطل رفع الصور.
5. شغّل `school-events/security-hardening.sql` لمنع الحذف المباشر للفعاليات على مستوى قاعدة البيانات. لا يحذف أي سجلات ولا يعدل جداول التأخير السابقة.
6. سجّل الدخول بحساب إدارة وبحساب موظف واختبر الحفظ والمراجعة ورفع صورة وعرضها وPDF وZIP. اختبر تسجيل الخروج أثناء التحميل؛ يجب أن تُمسح البيانات وألا تعود استجابة متأخرة إلى الشاشة.
7. على الهاتف افتح الرابط الجديد من المتصفح. النسخة المثبتة من المسار القديم قد تحتاج إزالة الاختصار القديم وإعادة تثبيته من الرابط الجديد. اختبر بريد التأكيد والاستعادة أيضًا؛ لا تكفي سلامة كود الرابط لإثبات إعدادات Supabase المنشورة.

## إنشاء مشروع جديد

`schema.sql` ثم `schema-features.sql` قالبان لمشروع جديد فارغ فقط، وليسا ترحيلًا للمشروع الحالي. استبدل **كل** `owner@example.invalid` ببريد المالك المتحقق منه في الملفين، وحدّث تحديد المالك في `app.js` عند استخدام مالك مختلف. يضيف القالب الثاني التوثيق والصور وأرشيف التقارير وسجل العمليات ودالة إدارة المسؤولين، مع RLS. يستخدم القالب Cloudinary للصور الجديدة؛ لا ينقل صور Supabase القديمة تلقائيًا.

## ما تم التحقق منه محليًا

- تنظيف الصور والوصف وقائمة الموظفين وسجل العمليات وأرشيف التقارير عند تغيير الحساب أو الخروج أو بدء المعاينة.
- رفض الاستجابات القديمة بعد الخروج، وعدم منح غير المالك صلاحية استدعاء إدارة المسؤولين من الواجهة.
- استخدام خدمة الصور الحالية في اختبارات التوثيق، وتصغير الصورة قبل الإرسال، وإعادة استعمال معرّف محاولة الرفع عند فقدان الرد لتجنب التكرار.
- اختبار خدمة الصور بخدمات بديلة: حساب غير مصرح، فعالية غير مملوكة، موعد مستقبلي، غياب التوثيق، بيانات غير صالحة، ونجاح حفظ سجل بصورة استجابة فارغة 201.
- إنشاء قاعدة معزولة من القالبين واختبار RLS ومنع اعتماد الموظف ومنع تعديل قرار التوثيق ومنع منح الإدارة لغير المالك ومنع كتابة بيانات الصور مباشرة من حساب المستخدم.
- الاختبارات لا تسجّل الدخول إلى Supabase الحقيقي ولا تكتب بيانات المدرسة.

## أوامر الاختبار

اختبارات المتصفح تحتاج Playwright وChromium. يمكن تحديد مسار Chromium عبر `CHROMIUM_PATH`.

```sh
node tests/documentation.cjs
node tests/session.cjs
node tests/images-function.cjs
```

اختبار خدمة الصور يحتاج Node 24 أو أحدث. لا يحفظ أسرارًا ولا يتصل بخدمات خارجية.

اختبار SQL يحتاج PGlite في مكان منفصل عن التطبيق:

```sh
npm install --prefix /tmp/school-sql-tests --cache /tmp/school-npm-cache --no-audit --no-fund @electric-sql/pglite
NODE_PATH=/tmp/school-sql-tests/node_modules node tests/schema.cjs
```

اختبار SQL يستخدم محرك PostgreSQL معزولًا. اختبار طلبين متزامنين على الخادم الحقيقي، وتكامل Supabase Auth/Cloudinary والبريد، يحتاج بيئة وحسابات فعلية؛ لا تغطيه البدائل المحلية.
